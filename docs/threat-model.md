# Threat model

Trust boundaries: web content → shell; other browsers' profiles → import; filter lists → rule compiler; page text → AI model; AI model → CLI helper; extensions → pages and shell; update source → app; other apps → URL handler; sync storage → app; disk.

The "Status" column records what the code enforces today. Algorithms, key lengths and TLS
settings per client are in `cryptography.md`.

| ID | Severity | Threat | Mitigation | Status |
|---|---|---|---|---|
| S1 | Critical | A web page reaches shell functions through a JS bridge or an internal page | No script message handlers in tab web views. Internal pages use a separate configuration and data store, bundled assets only, strict CSP; web content cannot link to, embed or navigate to them. | Tab web views get no script message handler; `tarn:` is blocked for web sources in `nav_policy`. Popups use WebKit's own configuration, so they keep the opener's request context. |
| S17 | Critical | Page text injects instructions into the Claude CLI, which can run commands and read files | Helper runs the CLI with tools and MCP disabled, fixed arguments, no shell, prompt on stdin, minimal environment, empty temporary working directory, timeout and output cap. Binary path is absolute, chosen by the user, and must not be world-writable. The helper accepts connections only from our signed app. If tool disabling cannot be confirmed, the provider refuses to run. | `tarn-cli-bridge` enforces the CLI rules: fixed arguments, `--help` probe, stdin prompt, only `HOME` and `PATH=/usr/bin:/bin`, own process group killed when the run ends or times out, and the binary plus every ancestor directory owned by the user or root and writable only by them, `wheel` or `admin`. Cancelling in the app stops the bridge, not the CLI it started. Not reachable from the packaged app only because `scripts/bundle.sh` does not ship the helper: the app runs without the App Sandbox, so a child would no longer inherit one. The XPC helper and its caller check are not built. An npm-installed CLI (`#!/usr/bin/env node`) does not start with that `PATH`. |
| S2 | High | Prompt injection makes the AI leak data or act | The model has no tools in any provider. Output is rendered natively as text: no remote images, no auto-opened links. Grouping returns schema-validated JSON limited to the tab IDs sent and is applied after confirmation. Context is limited to the active profile; query strings are stripped from URLs. | Not built. |
| S3 | High | API token or page content leaks | Token only in the Keychain. Content leaves the device only after an explicit click with a visible indicator. AI is unavailable in the private profile. We never read the CLI's stored credentials. | Not built. |
| S4 | High | Malicious update | EdDSA-signed updates, HTTPS, downgrade protection, signing keys only in the signing environments of the release workflow. On Windows, `platform::updater` reads `windows-update.json` next to the appcast: its Ed25519 signature (the Sparkle key in `packaging/updates.conf`, compiled in) is checked over the exact bytes before anything is parsed; the installer must come over https from this repository's release downloads, match the signed length, SHA-256 and its own Ed25519 signature before it is written, and is hashed again through a handle that bars writes while it starts; only a later version is offered; feeds are capped at 64 KiB and installers at 512 MiB. Windows releases ship the unsigned installer CI built: the release workflow's signing job, which runs no build code, signs that run's installer and its `windows-update.json` with the update key (`scripts/windows-feed.sh`, its URL limited to this repository's release downloads), so installs have no Authenticode signature; `scripts/sign-windows.ps1` (Authenticode) is not part of CI and no certificate is set up. Remaining on Windows: the installer is not Authenticode-checked by the updater, so the Ed25519 key is the only anchor, and a replayed feed that lists the running version still counts as a verified check (as on macOS) until releases carry an expiry. Repository: two-factor login, branch protection, pinned actions, no secrets for fork pull requests. | CI actions pinned by commit hash; no job that pull requests, issues or comments can start runs on a self-hosted runner: enforced only by the runner group's "Selected workflows" limit and fork-approval settings in `release.md`, applied by hand, since a fork pull request runs its own edited workflow; `scripts/check-workflows.sh` in CI is a merge-time lint that keeps such jobs out of `main`, not a control on what a pull request can schedule; `.github/CODEOWNERS` covers the workflows, `codesign-app.sh`, `bundle.sh`, `packaging/`, the lockfiles and manifests and the embedded signing keys (owner `@Quavon-dev/maintainers`), and `main`'s ruleset requires approval of the most recent push and dismisses stale approvals (settings by hand); Chromium updates are proposed, tested, merged and built by `chromium-update.yml`, and signed and published by `release.yml` only after a maintainer approves its `release-signing` deployment. Updater: Sparkle 2.10.1, pinned by SHA-256, verifies the archive's EdDSA signature before extraction, requires a signed feed and refuses older versions; the feed (the latest published GitHub release's `appcast.xml`) and the public key are in `packaging/updates.conf` and only release bundles carry them; the private key, the Developer ID certificate and the notary API key are secrets of the `release-signing` environment (deployments from `main` and `v*` tags, a maintainer's approval) and the `nightly-signing` environment (deployments from `main` only, no approval) and the private key has an offline backup; only the `sign` job enters them, runs no build code, imports the certificate into a temporary keychain and writes the other keys under `RUNNER_TEMP`, and deletes both when it ends. A compromised build job or dependency build script holds none of them, but a workflow or script changed on `main` runs with them on the next nightly without approval and could sign a feed that Release users accept, since both channels share the update key (Sparkle takes one `SUPublicEDKey`); code-owner review of `.github/` and `scripts/` on `main` is what stands in the way, and `scripts/appcast.sh` signs only a notarised Tarn of team CFV35FGSHF whose version matches the tag. The feed URL comes from Info.plist through the updater delegate, never from user defaults; with Settings › General › Nightly builds on it is the same file in the `nightly` release (`platform::updater::nightly_feed`), on macOS and Windows. Nightly builds carry `<latest release>.<run>` versions and are signed with the same keys: every commit merged to `main`, including engine updates `chromium-update.yml` merges with the update app's bypass and a CEF archive only its own download checked, reaches users of that channel signed and notarised within a day, with no release review. Nightly feeds carry their channel inside the signed bytes (`sparkle:channel`, the Windows feed's `channel`), and the Release channel refuses them, so a nightly feed uploaded to a release is not offered to Release users. A nightly on the Release channel counts the release feed as current for its release version (`channel_version`) and is offered only a later release. A check counts as verified for the Chromium staleness gate only if the signed appcast lists the running version or a later one, so an old appcast replayed through a release asset no longer keeps Chromium open; one listing the running version still does. A feed that fails verification still offers items in Sparkle's fallback mode (no critical marking); the archive signature still applies. Tampered and older updates not yet tried against a real feed. Windows, Linux and mobile release files are built unsigned from pinned containers and a pinned rustup-init but with unpinned distribution packages and Gradle dependencies; they are attested by a job that runs none of their code, and each build job can add only its own file names to the release. A release run starts from a `v*` tag push (tag creation limited by ruleset), from `start-release.yml` on `main` (any account with write access can start it; it builds every client without keys, and only after a maintainer approves the `release-signing` deployment does the `sign` job create the `v*` tag with the update app, whose key that environment then also holds, so this tag is the app's, not a maintainer's signed tag), a manual `workflow_dispatch` on an existing `v*` tag, which any account with write access can start and which builds macOS alone, or `chromium-update.yml`; it refuses a tag that already has a release and publishes only after the `release-signing` deployment is approved. `nightly.yml` publishes the `nightly` pre-release without approval. The signed zip, disk image and feeds are in `SHA256SUMS` and the attestation. |
| S18 | High | Malicious or compromised extension | Per-profile install, per-site permission prompts, hash recorded, no silent updates, off in private mode by default, no access to internal pages or other profiles. | App and Official extensions get every site they list without a prompt while Settings › Extensions › "Allow extensions on every site" is on, which is the default (`Pref::ExtensionsEverySite`); Unverified ones always ask per site and Lockdown hosts stay denied. `tabs.create` from an App extension opens a web page as a normal tab through `nav_policy`, at the pop-up rate (3 in 10 s) and never with a private-network address as its URL (S10). Open: that tab is a user load, so a redirect of its URL to a private address is followed. With the global switch on, an update that asks for more sites is not held back. Only Safari web extensions bundled with apps in `/Applications` are offered (`engine::extensions`); nothing runs until the user turns an extension on for the current profile in Settings › Extensions, which lists every requested permission and site pattern. Turning it on grants all of them (no per-site prompts). Each profile has its own `WKWebExtensionController`: storage is keyed by the profile's own data-store UUID, also when it shares website data with another profile, the private space gets an in-memory controller with nothing enabled, Lockdown profiles and Lockdown-level views get no controller, and hosts with a Lockdown override are denied to every extension (checked: the content script stops answering), because a link into such a host keeps its view. An extension sees only the tabs of its own profile. Its `safari-web-extension://` origin (Safari's scheme, which Bitwarden's inline menu requires), which pages can see, is derived from the profile's data-store UUID, so it differs per user and profile; sites that probe for Bitwarden's Safari pages find it as they would in Safari. `windows.create` opens a window only for the extension's own pages (Bitwarden's unlock, passkey and edit popouts), at most four per extension, each side between 200 and 1000 points and the height kept on screen; the window's top-level navigations are held to the extension's own pages, because it has no navigation policy or Shield, and it closes when the extension is turned off or its data is removed. Only the extension that opened it sees it. Frames inside it are not restricted and it shows no origin chip, as with the extension's toolbar popup. Native messages and native ports are answered only for an app extension whose code signature is Bitwarden's (`com.bitwarden.desktop.safari`, signed by team `LTZ2PFU5D6`, or by Apple for the Mac App Store with that team's entitlement), checked when extensions are discovered, and only for the four Bitwarden uses (`copyToClipboard`, `readFromClipboard`, `sleep` with at most 16 pending, `showPopover`); a native port (`connectNative`) is accepted only for Bitwarden's app id, at most four per extension, closed with the extension, and answers only Bitwarden's biometrics questions as its Safari app extension does: Touch ID through LocalAuthentication, then the user key the Bitwarden desktop app keeps in the login keychain (`Bitwarden_biometric`, account `<user id>_user_biometric`), read off the main thread after Touch ID succeeded and handed only to that port; one Touch ID prompt at a time, naming the extension; once Bitwarden has run in a profile, until Tarn restarts, pages there (not at Lockdown) are told that passkeys and conditional mediation are available, as in Safari, but only in frames where `navigator.credentials.get` has been replaced again, by Bitwarden's page script or the page itself; WebKit says no without Apple's browser entitlement and refuses conditional requests at once, so in those frames such a refusal of a request with an abort signal stays pending until the page aborts it, as Safari's conditional UI does, and Bitwarden's answer is not cut short; elsewhere WebKit's own answers are returned, the availability one after waiting while the document still parses, at most 40 checks 50 ms apart; clipboard writes need the granted `clipboardWrite` permission and reads also need `clipboardRead` in the manifest, which Settings then lists. Deleting a profile removes its extensions' data through WebKit and then WebKit's folder for it, whose `State.plist` names each extension; "Delete everything" removes the data and restarts the profile's extensions. Tarn has no internal web pages to reach. Extensions can also be installed from a GitHub repository, the signed official catalog (own ed25519 key, domain-separated signature, rollback and 30-day freshness checks, a revoked set that only grows) and `.zip`/`.crx` files: archives are unpacked with strict name, size, depth and type checks into read-only per-install directories; storage is keyed by a random install id; the tree hash is recorded at install and checked before every load, `.appex` bundles included, and a mismatch turns the extension off and drops its site grants; trust labels and the Bitwarden privileges (native messages, clipboard read, passkey script, pop-out windows) follow the install source, never the manifest; unpacked extensions show a popup only after a toolbar click. Host access is per site: the grant-all loop is gone, WebKit's own URL prompt becomes a tab-modal Allow/Deny with Remember (Once lasts an hour), decisions are stored per install and profile, and App and Official sources may be switched to "Allow on every site", which turns off when an update asks for more sites (without effect while the global switch is on). Extension pages, workers and popups get the profile's private-network and HTTPS rule lists. `Tab` refuses `loadURL`, reload, back, forward and zoom without access to the tab's page. Updates are a new install with the same prompt, never automatic. |
| S5 | High | Origin spoofing; a sidebar-only UI hides the URL | Origin chip always visible; registrable domain emphasised; punycode for mixed-script names. Prompts and dialogs show the origin and are tab-modal. | Origin chip shows the host as parsed by `url` (IDNA to punycode); a `blob:` page shows the host of the URL it wraps and a page without a host (an opener-filled `about:blank`, `data:`) shows only its scheme (`about:blank`, `data:`), as does its tab title when the page set none, so the chip is empty only when no page is loaded. Without the selector no hop counts as the user's. For the chip, `user_navigation` still covers the time until the user's load commits or any load fails. The link peek header uses the chip's label (`toolbar::site_of`). Dialogs, permission and sign-in requests are tab-modal cards naming the origin (shortened from the left so the registrable domain stays visible) and the embedding page for frames; a permission card's Allow and Remember ignore clicks for 700 ms after the card becomes visible, a banner above it appears or leaves, or the window becomes active (which also covers leaving element fullscreen). | S6 | High | Dangerous schemes and untrusted URL sources | Allowlist `http`, `https`, `about:blank`, `blob`. `data:` not at top level. `file:` only by explicit user action. `javascript:` rejected in the command bar and on paste. External schemes prompt each time. URLs from other apps, drops and sync pass the same policy. | `nav_policy::decide` with table test; applied to typed input, command-line URLs, restored tabs and session snapshots, main-frame navigations, redirects and popups. A page's external-scheme request shows a banner naming the origin of the frame that started it ("A page" when opaque or while a main-frame load is in flight, so a server redirect is never credited to the page or frame that linked to it), only in its own tab, until that tab's next commit or close; while it shows, further requests are dropped, and "Open" ignores clicks for 700 ms after it, or any banner above it, appears, and again when the window becomes active. Links other apps send (the default-browser case, `shared::open_urls` through GPUI's `on_open_urls`) pass `decide(ExternalApp)`, at most 10 in 10 s across the app (the rest are dropped with a toast), and load as a page's link (`WebView::load_link` with no opener), so S10 refuses a local target or any redirect hop into the local network with its usual notice; typing the address opens it. A loopback link (`localhost`, 127.0.0.0/8, `::1`) opens as typed while Settings › Privacy › Open localhost links from other apps is on (the default), since developers open local servers from terminals and editors; the accepted risk is that a link from a remote sender (a mail) can then reach a service on this computer, as a typed address could. Off, it gets the notice. Other local addresses always get it. The notice offers Open Anyway, which loads the address as the user's own navigation. Chromium tabs do the same: their `load_link` sets no shell mark, also for a load held until the view is ready, so `on_before_browse` credits the page (a Chromium integration test is not written yet); such a load is not a user's, so it does not bridge WebKit's cookies first and the site may open signed out in Chromium. Open: public names that resolve to private addresses (`nip.io`-style) are not recognised. |
| S19 | High | Sync storage is read or tampered with | Client-side authenticated encryption; remote data validated as untrusted input; secrets and cookies never synced. | Not built. |
| S7 | Medium | TLS downgrade or click-through | WebKit's default trust evaluation, never custom acceptance, and no bypass at any level. | S8 | Medium | Local data at rest | File permissions and FileVault (documented). Private profile in memory only. Wipe covers data store, history, kept page text, protected-site hosts (at most 200 a profile, the busiest kept, since a page can choose the hosts it is upgraded to), favicons, site zoom levels, muted sites, downloads list and saved `interaction_state`. | S9 | Medium | Cross-profile leaks through shell features | Favicons, suggestions, permissions, downloads, extensions and AI context keyed by profile. A link peek (⇧-click) uses the opener's profile data store and Shield rules and moves only into a tab of that profile. A space rule (`space_rules`, a host or `*.host`) opens a new tab of a matching URL in the ruled space, so in its profile: only for argv and macOS open-URL requests (after `nav_policy` `ExternalApp`), command-bar new tabs and pop-ups from a link the user activated (`target=_blank`, ⌘-click; WebKit's `LinkActivated`) already allowed by `nav_policy` and the pop-up rules, never for a script's `window.open`, which keeps its opener for sign-in and payment flows, and never for a navigation inside a tab. | S10 | Medium | Public sites attacking localhost or LAN devices | Content rule blocks requests to loopback and private address ranges unless the top-level page is itself local. Web Inspector only in the dev profile or by toggle. | Rules generated in `shield::rules`, including userinfo, IPv4-mapped IPv6, trailing-dot, CGNAT (100.64/10) and IPv6 link-local (fe80::/10) forms; each host pattern ends at the path or a numeric port, so `127.example.com` or `localhost:x@evil.com` as the top page does not lift the block, and a top page with credentials or an IPv6 form embedding IPv4 (`::ffff:`, NAT64) never counts as local. A Shift-clicked link is loaded by the shell as a peek, so it gets the same public-to-private check before `PeekLink` is emitted. The peek loads with `WebView::load_link`, which is not a user navigation: the first URL and every redirect hop get the check, judged from the opener's origin until the peek has a page (`crates/app/tests/redirects.rs` covers the user's own loads across redirects). `*.localhost` top pages count as local and rely on the resolver answering loopback for them. Rules compile asynchronously; a WebKit view holds its first load (or session restore) until its level's built-in list is attached, and if that list fails to compile the view loads nothing and shows the error. Chromium tabs get no rule lists; `engine::request_filter` checks each request with `shield::rules::is_local`, which accepts the same forms, and treats the top page as local only when both the main frame's URL and Chromium's first-party site for the request are local, so a local page just left cannot exempt the next page's first requests; a request filter that has no Shield snapshot yet cancels everything. WebSocket handshakes from Chromium tabs never reach that filter, so a public page in Chromium can still open a WebSocket to a local address (open). At Strict, Chromium tabs drop the cross-origin `Referer` header but the next page's `document.referrer` still names the page left (open). Web Inspector is enabled only with Settings › Developer on or in a developer profile (in Chromium tabs, only then does the page menu keep Chrome's Inspect); the local-server probe connects only to 127.0.0.1 on a fixed list of dev ports with a 300 ms timeout. JSON documents are read from the client world with a size cap and parsed with depth, node and text limits (`devkit::json_view`). Both engines also refuse a script-started main-frame navigation from a public page into a local address (`nav_policy::into_private_network`); a navigation the user started (typed, a click in Chromium, or the shell's back, forward or reload) keeps through its redirects. Back, forward and reload count as the user's only when the shell started them, never by navigation type, so a script's `location.reload()` or `history.go()` that a server redirects into the local network is refused. The page left is judged by its origin: a `blob:` page by its inner origin, a WebKit page without a committed origin (a new popup, `about:blank`, `data:`) by the origin of the frame that started the navigation, and anything opaque or without an http(s) origin as public. A back, forward or reload with nothing to go to does not count, nor does the reload after a page's process ends, since a page can end its own process. In WebKit a clicked link and WebKit's own swipe back from a public page into the local network are refused too, since WebKit reports them like a script's; the user types the address, or presses Open Anyway on the notice, which names the address. | A page may also not send the top frame or a new window from a public origin to a private address (WebKit `decide_policy`, `create_web_view` and Chromium `on_before_browse`); typed addresses still load. If the built-in rule list fails to compile, a banner says the protection is off.
| S20 | High | Tampered or hostile filter lists | Bundle signed by a separate CI key and verified in the app; size caps per file kind and in total; last good bundle kept. Lists are data only: network rules, plain CSS selectors and domains, never scriptlets or code. **Page scripts on Android (S1, S14).** Contract v3's reader, page-text, Find in Tabs text and element-picker
scripts run in the page's own world on Android, which has no isolated world without a JavaScript bridge. A
page can see and change those scripts' globals and forge their answers (an async script's answer is held
in a `window` property with a random 128-bit name until the component polls it). What a forged answer can
do is bounded in Rust: `Article::parse` and `clip_history_text` keep only plain text of the page's own
document, Find in Tabs matches the query in Rust (the query never reaches the page), and a picked selector
is stored only when `valid_zap` accepts it, for the host the tab still shows, so a page can at most hide
parts of itself or put its own text into its reader view or history search. Scripts never run when
JavaScript is off (Lockdown). They run only when the user asks: opening the reader, Find in Tabs (every
live tab's page, once per page while a search goes on) and the element picker; the reader probe other
platforms send after each load is never sent on Android. The one exception is full-text history, off by
default: while it is switched on, every finished http(s) page of a normal space runs the page-text script,
so a page can notice a Tarn user who turned it on (a script ran in its world). A page that watches its own
world can also see the reader, Find in Tabs and picker runs when the user starts them. Site CSS and zaps are added per host with `addDocumentStartJavaScript`
limited to that host's default-port origins.

**Themes (S29) on Linux, iOS and Android.** The clients read the same `browser_core::theme` tokens through
`tarn_nsh_shared::theme`, and security UI (address field at rest, "Not Secure", the Shield glyph, prompts,
the external-app notice, theme badges, Reset Appearance) draws from `Secure`, the scheme's built-in colours,
line for line the Mac's (a test compares the two and applies a hostile theme). The theme's interface font
(`Theme::font_family`) is set on each shell's root view; `secure_surface`, `secure_button`, the
address field, the Shield label and start-card chip, the theme badges and Reset set the system font, so
security UI keeps it. Installs, withdrawals and the
website-styles switches go through `browser_core::theme_library`, which the Mac also uses. Website sheets
(`theme_library::profile_sheets`) are never sent for private spaces, burner tabs or safe mode, and reach the
engines as a `themeStyles` prop that `engine::page_scripts::theme_sheets` validates (host patterns, 64 KiB
total). Linux runs them in the `tarn` isolated world before the user's own CSS, never in a Lockdown view, and
the script returns at once on a host whose level is Lockdown, set for it or by the profile default
(`page_scripts::outside_lockdown`), since WebKitGTK swaps in the
Lockdown view only after commit; iOS runs them in the client world and builds a Lockdown view before such a
load. Android has no isolated world, so the page-world path of site CSS (S28)
carries them: one document-start script holds every theme sheet, limited to the origins the theme names
(`*` for every-site sheets), and each host with its own CSS or zaps gets a script with the matching theme
sheets first. This is accepted because theme sheets are re-serialised CSS that never contain the user's data;
what a page gains is the theme's sheets for other sites it names (public in the theme file) and the
`tarnSiteStyle` note, which a page can already see on its own host. Lockdown turns JavaScript off on Android,
so no sheet runs there. Withdrawals reach Linux through the cached filter bundle at launch and every client through the theme
catalog (cached index at launch, merged again on each fetch); iOS and Android download no filter bundle,
so on them a withdrawal arrives only with the catalog (`docs/mobile-plan.md`). Shift at launch (safe mode) exists on Linux only (GDK keyboard modifier state); iOS and
Android have no modifier key at launch and offer Reset Appearance instead. GitHub installs, update
checks and the signed catalog use the Mac's code (`browser_core::github`, `browser_core::theme_fetch`): the
host list, HTTPS only, every redirect checked against the list, at most three, and the size caps live in
`github::follow`, so a client only makes one request (`github::Hop`) with no redirect following, no proxy,
cookies, cache or credentials, a fixed user agent, a 10 s stall and 120 s total limit, and a read that stops
past the cap: libsoup on Linux (a session made on the fetch thread), `NSURLSession` with an ephemeral
configuration on iOS, `HttpURLConnection` in the Android host. For the test servers, Android debug builds may send these
requests through a loopback proxy named in a file in the app's own storage (`debug-proxy`), and an iOS
build compiled with `TARN_TEST_PROXY=127.0.0.1:<port>` through that loopback proxy; release and store
builds use no proxy. The pending card is a `secure_surface`.
The catalog key is unset, so the Official section is hidden on every client.

**Burner tabs (S8).** iOS: a non-persistent `WKWebsiteDataStore` per burner, released when it burns. Android:
a throwaway `ProfileStore` profile per burner in the main process, which WebView keeps in use until the process
ends, so it is deleted at the next launch's sweep and, like Lockdown, is on disk until then; no burner
in the `:private` process.

**Android private space (S8).** The deviation decided in `docs/nsh-plan.md` §9 is built: private browsing
runs in the `:private` process with its own `setDirectoryBasePaths` folder, deleted on close and swept at
launch; the private activity disables its Recents screenshot and sets `IME_FLAG_NO_PERSONALIZED_LEARNING`;
the launch sweep deletes `AwOriginVisitLoggerPrefs.xml` whenever no private process runs; a private
activity Android restores by itself finds no session token, closes and triggers the sweep. Each was checked
on the phone and tablet emulators (`docs/mobile-plan.md` M3). The wording below holds for these builds:

"On Android the private space cannot keep data off disk: the system WebView has no in-memory store. Private
browsing runs in a separate process with its own WebView data directory inside the app's
credential-encrypted storage; that directory is deleted when the private space closes and, after a crash,
force-stop or WebView update, at the next app start. Until then it is readable by anyone with root access
or a forensic image of the unlocked device. Deletion is a file unlink, not a secure erase. WebView also
records reversible hashes of visited origins in the app's shared preferences, which normal mode writes as
well; Tarn deletes that file at each launch while no private session is open. The private activity is
excluded from Recents screenshots and its text fields opt out of keyboard learning."

Recents: the stored snapshot is blank, but while the private task is in front, the launcher's live tile
shows it. Lockdown in the main process uses a throwaway `ProfileStore` profile, which stays on disk until the
next launch, like the private space. Not verified on a physical device.

## Who patches what

| Layer | Patched by | Automatic? |
|---|---|---|
| WebKit (rendering, JavaScript, TLS, content sandbox) | Apple | Yes, with macOS updates. We cannot ship a fix ourselves. |
| Shell code | Us | Reaches users automatically through Sparkle once released. |
| Rust dependencies, GPUI, Sparkle | Us | Detection is automatic; review and release are manual. |
| Filter lists and domain sets | List maintainers, prepared and signed by CI daily | Yes. |
| Extensions | Their authors | Only when the user installs a new version. |
| Themes | Their authors; withdrawals by us | Updates only when the user confirms one; withdrawals arrive with the daily filter lists. |
| Claude CLI, Ollama | Their vendors | Outside our control. |

## Risks that remain

These cannot be closed by this design; they are documented for users.

- A WebKit zero-day stays open until Apple ships a fix and the user installs it.
- Deep fingerprinting protection and encrypted DNS inside the app are not possible on WKWebView.
- The private-network rule matches addresses, not DNS answers, so DNS rebinding is only partly covered.
- An extension the user grants broad permissions can read those pages.
- Website styles from a theme, once turned on, can make text on the sites they name hard to read.
- Malware already running as the user can read the profile database and Keychain items it is allowed to see.
- Once a user allows Tarn to read another browser's Safe Storage key, macOS may let Tarn read it again without asking.
- With Claude enabled, Anthropic receives the page content the user sends.
- No blocker catches every ad: ads served from the same host and path as content, and video ads
  stitched into the stream by the server, pass. YouTube can change its player and break the
  YouTube script until the bundle's `youtube.json` or an app update follows.
- WebKit's fraudulent-website check asks Apple, which uses Google Safe Browsing, about hashed
  address prefixes; the malware switch turns it off together with the lists.
